Tools: who runs them

Code tools run in orq.ai. Function tools run in your process. MCP tools run on a server you register.

CODE TOOL · RUNS IN ORQ.AI

Python registered in orq.ai. One request runs the whole loop.

USE IT WHENThe logic can live in orq.ai.

FUNCTION TOOL · RUNS IN YOUR PROCESS

Your code runs it and sends the result back to the model.

USE IT WHENThe tool must reach your own database or private API, or needs your own approval step.

MCP · RUNS ON AN MCP SERVER

Register the server in orq.ai. Agents get its tools through the MCP Gateway.

USE IT WHENThe tools already exist as an MCP server, yours or a vendor's.

MCP vs MCP Gateway

MCP is the protocol for tools. The gateway is the control point you put in front of it.

MCP serverClient talks to the server directly
MCP GatewayClient talks to one governed URL
Tools exposed
Everything the server offers. A client allowed to read data can also change it.
An allow-list per server: you choose which of its tools clients can see.
Who is calling
Whatever credentials the server itself checks.
A bearer key per client, so every call has a named caller.
What you see
Only what the server logs, if it logs.
Every call logged: exposed and upstream name, status, latency, key. Denied calls too.
Use it when
One trusted client and a server you own. A managed agent attaches by tool id.
Several clients, coding agents or shared tools, and some tools must stay out of reach.
Sources: modules/10-mcp-gateway/README.md (why: tools leak, allow-list per server, every call logged incl. denied; three entities MCP Server, MCP Gateway, key).

AI Gateway: key concepts

Four gateway controls and the span that records them.

MODEL APrimaryCall configured primary model.
configured error
SAME MODELRetry × 1Retry that same model once.
still failing
MODEL BFallbackCall configured fallback model.
  1. RetryRetries the same model on error codes such as 429 or 503.
  2. FallbackIf the primary still fails, the next configured model answers.
  3. CacheAn exact repeat with the same model, input and parameters can be served from cache, avoiding provider cost.
  4. Load balancingWeights such as 50/50 set traffic proportions; a short run is not guaranteed to split evenly.
  5. SpanOne step in a trace, such as a model call or a fallback decision.
Sources: https://docs.orq.ai/ai-gateway/features/retries; https://docs.orq.ai/ai-gateway/features/cache (exact-match request and provider cost); https://docs.orq.ai/ai-gateway/features/load-balancing. API keys: do and do not

Agree on these defaults with IT before keys are handed out.

DO

  • Prefer restricted keysGrant only what the app needs.
  • Use one key per app and projectA leak then has a smaller blast radius.
  • Use service account keys for CIThey outlive any one person.
  • Set a budget where appropriateA budget is a spend control, separate from permissions.

DO NOT

  • Share one broad key across teamsUse separate keys so access and usage can be managed.
  • Put keys in code or chatUse the secret store.
  • Use a personal key for a shared jobIt stops when that person leaves.
  • Assume the selected grant was storedRead back the key's project and permissions.
Source: https://docs.orq.ai/ai-studio/organization/api-keys. Repo: modules/05-budgets-keys/README.md:203-206 records a September 2026 API-creation anomaly: one path stored a requested restricted/single key as all/all.
